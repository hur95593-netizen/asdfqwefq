# 避坑与完整性验证

## 常见失败及修复

| 失败 | 为何会漏/错 | 修复 |
|---|---|---|
| 只打开 index.html | MPA 孤立页面、SPA 深层路由未被枚举 | 原始候选清单与入口/路由图双向对照 |
| 按 HTML 数统计页面 | 说明页、模板与真实入口混在一起；SPA 一入口多视图 | 给每个候选定角色，业务 PAGE 与物理文件分开 |
| 按说明文件名读取 | 日期命名 txt、HTML 注释或页面内说明被忽略 | 判读所有自有 md/txt/html，记录“无产品条款”结论 |
| 把补充文档整体归到一条需求 | 同段新建/复用/条件要求会互相覆盖 | 条款拆分，每条 note 映射 REQ/MOD/QUESTION |
| 看到“复用”就删模块 | 否定、建议、旧引用、局部样式复用含义不同 | 保留上下文，判断对象与适用范围，先统一 scope |
| scope 在各 agent 内各自决定 | 并行草稿可能重新带入已排除模块 | 主 agent 发布统一范围表；正文使用 included 白名单 |
| 排除沿 import 传播 | 共享组件被误删，宿主需求消失 | 只沿被复用模块内部拥有关系排除；宿主明确新增另记 |
| 截图当需求全貌 | 隐藏状态、事件分支、接口参数无法从首屏得知 | 源码+补充说明+运行观察交叉核对，逐交互检查 |
| 运行显示错误就写错误需求 | 环境缺资源、真实产品错误态不同 | 区分验证环境失败与产品期望；无依据放缺口 |
| mock 只复制几条 | 丢记录、特殊值、注释、JS 类型、编码 | 完整原始文件 byte-exact 备份，样例是单独派生物 |
| 使用 eval/导入解析 mock | 会运行任意输入，并改变数据 | 静态解析、原始快照；生成器只记录源码与依赖 |
| 用正则声称全部数据已找到 | 跨文件对象、DOM、动态生成、异名变量可能漏检 | 人工/agent 复核自有源文件，必要时 include-source 重跑 |
| 机器检查通过就报全部完成 | 校验器只能检查已经写入的记录 | 独立 agent 从原始材料反查遗漏，报告语义边界 |

## 两层验证

第一层运行 `scripts/validate_output.py`。脚本检查输出契约、清单是否逐项判定、ID/关联、范围、Markdown 项目集合和 mock 原始快照 hash；`verification.json` 区分 failed / incomplete / passed。检查报告不得人工改成 passed。

第二层由独立 subagent 对照输入材料复核；资源有限时主 agent 用新一遍原始材料检查承担这一环，在 review.md 说明独立性限制。只给审查 agent 原始输入、Skill、输出路径和已知运行限制，不给预设“应通过”结论；要求提供具体源位置和遗漏/污染证据。它不应仅检查正文是否包含固定标题。

最终交付含三个不同结论：机器关联/文件完整性、语义提取覆盖、运行验证覆盖。三者不可互相代替。未知路由、未读文件、未决条款和未运行关键行为会限制“全部完成”的声明；可以交付清晰标注的可用草稿。

## 语义复核清单

1. **发现分母。** 重新从源目录核查孤立 HTML、SPA 路由/状态分支、动态 import、说明候选和生成目录。每个候选有去向；模板/依赖的排除有可解释理由。有限枚举与运行时动态范围分开。
2. **说明闭环。** 每份说明逐段检查：明确补充、否定、条件、版本、同名范围、交互顺序、成功/失败/取消分支。混合条款拆分；每条 note 有正确目标而非仅存在一个任意目标。
3. **范围隔离。** 对每个 excluded module 搜索正文、验收、字段、技术建议、mock 参考中的名称、别名、所属 REQ/MOCK ID 及内容释义。检查改名后的隐性重建要求。机器禁词仅是补充，不能发现释义污染。
4. **需求真实性。** 每条 REQ 的证据真正支持规则和验收；不能仅有一个 EV ID 却内容不符。区别现有实现、明确补充、惯例建议。没有输入依据的限制、权限、API 和状态不写成承诺。
5. **交互状态。** 按输入控件、事件监听器、跳转和状态分支反查 interactions；按 interactions 反查正确页面与需求。空、加载、错误、禁用、取消等只统计确有证据的分支。页面 verified 必须有真实 runtime 证据，且说明已验证的具体场景范围。
6. **数据恢复。** 从源文件重新选取代表性多类型样本，核对备份 hash、编码、转义、重复记录和边界值。全部候选已裁定；not_mock 有理由；动态生成数据只声称保存生成器。规范化结果未丢字段，或明确列出转换损失。
7. **文档可实施。** 开发者能知道在哪里触发、输入什么、结果如何、边界在哪里、如何验收以及参考哪份样本；没有重复且矛盾的共用需求，没有待定模板语句。
8. **真实限制。** 页面启动失败、外部依赖不可用、文件跳过、未恢复动态路由、待定复用范围都在内部报告中可定位；正文只列纳入范围的相关限制，不借缺口章节输出排除模块需求。

## 覆盖报告读法

`已裁定入口数 / inventory 入口候选数` 只能说明候选处理率，不能证明真实路由全部发现。`已处理交互数 / 已发现交互数` 需要配合源码反查，不能称为“全部业务需求覆盖率”。对于没有候选的分母显示 N/A 或 `0/0（未发现）`，不写 100%。

已复用、说明页、非业务资源可算“已裁定”，但不能算“已实现”或“已运行”。mock 快照存在与 mock 业务含义已恢复是两件事：完整保存生成器源码不意味着已有每条生成结果。运行验证应给页面数和具体场景，不把一次截图等同页面所有交互通过。

## Skill 自身的回归验证

每次变更辅助脚本后运行：

```sh
python3 -m unittest discover -s "$SKILL_DIR/scripts/tests" -v
```

这些测试应核对可观察的不变量：不能遗漏未链接入口候选；候选不会被当作最终结论；原始备份字节不变；不跟随链接读出边界；输出不覆盖输入；缺引用/重复ID/范围污染/快照篡改导致失败；static_only/deferred/pending 导致 incomplete。

对提取规则的大改，在独立临时输入中做一次端到端执行，至少覆盖：多入口+孤立 HTML、单入口 React/Vue 多路由/视图、混合形态、md/txt/html 补充说明、整模块复用/不要复用/仅复用样式、源码与说明冲突、JSON/inline/DOM mock、动态生成器无法恢复、无法运行的真实降级。不能只运行格式验证器就宣称 Skill 行为已经验证。
